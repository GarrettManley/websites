mtga-companion is a tracker for MTG Arena that runs on my own machine. It follows the log the game writes as it runs, through a shared read-only handle, and never touches the game's memory, network traffic or input. It keeps every log entry in SQLite, rebuilds matches and full game state from them, and answers questions about my play through fifteen read-only tools that Claude Code calls over MCP. A separate always-on-top overlay shows the match in progress.

The failure I designed against is a wrong number. Every rate carries its sample size and a Wilson interval, and below ten games a cell shows only wins and losses. The rest of the design follows from that.

## Architecture

Data moves one way through three layers: the raw log as captured, the tables derived from it, and the views that statistics read. Each layer reads only the one above it, so anything below the raw store can be dropped and rebuilt.

<Architecture />
</Figure>

1. The game writes `Player.log`. Capture reads it through a shared handle and never writes to it.
2. Capture stores each log entry before anything parses it.
3. The raw store can reproduce the original bytes exactly.
4. The parser is a pure, versioned function from raw entries to facts.
5. Derived tables hold matches, games and game state. A rebuild drops them and replays the raw store.
6. Fourteen SQL views and a statistics layer turn facts into rates with sample sizes and intervals.
7. The MCP server exposes fifteen read-only tools over stdio. Claude Code is the client.

Beside the pipeline, the live overlay is a separate process that reads the store read-only and replays the current match in memory.

## Decisions

<Decision n={1} title="The log is the only source of truth">
<Fragment slot="chose">

Capture stores every log entry before anything parses it. Matches, game state and statistics are derived from that raw store, and can be thrown away and rebuilt.

</Fragment>
<Fragment slot="why">

A number I can't trace back to raw events and recompute is a number I can't trust. It also means a parser fix never needs a re-capture: the games already played are still there.

</Fragment>
<Fragment slot="rejected">

Reading the game client's memory or network traffic.

Notes taken while playing as the ground truth. I dropped them; the expected values in the tests are read by hand from the raw log.

</Fragment>
<Fragment slot="proof">

A test ingests a recorded session (19,378 entries, 62 MB of log text), exports it again, and requires the same SHA-256.

The first version would have failed it. An early check found line endings folded and text decoded lossily, so "lossless" was only true row by row. The rule since: a lossless claim needs a file-level round trip.

</Fragment>
</Decision>

<Decision n={2} title="Rebuild equals incremental">
<Fragment slot="chose">

The parser is a pure function from raw entries to facts, and it carries a version number. A rebuild drops every derived table and replays the raw store. Incremental parsing during play must leave exactly the state a rebuild would.

</Fragment>
<Fragment slot="why">

Every parser fix becomes the same operation: bump the version, rebuild. The first parse after a bump is a full rebuild, so old and new parser output never mix.

</Fragment>
<Fragment slot="proof">

Two tests parse recorded sessions the way live play does (64 KiB steps, a parse at each match completion, process restarts partway through) and compare a fingerprint of every derived table against a from-scratch rebuild.

In production, the move to parser version 4 rebuilt a store of about 151,000 entries in 10.6 seconds.

</Fragment>
</Decision>

<Decision n={3} title="A regression every gate missed">
<Fragment slot="chose">

Three nets for query cost:

- A test counts the work SQLite's virtual machine does for each card query on a fixed seeded store, and fails at 25% over a committed baseline.
- Query-plan tests pin the join orders that matter.
- Any change to a view needs a timed A/B of the parent build against the candidate, on the same copy of the store, before it merges.

</Fragment>
<Fragment slot="why">

A correctness fix to one view changed nothing in its output, but it let the query planner choose a different join order. Three card tools got 2.4 to 3.1 times slower while every test stayed green, because the rows were identical. It surfaced only when the tools were timed at the start of the next sprint. A bisect named the commit.

</Fragment>
<Fragment slot="rejected">

A wall-clock threshold in the automated gate. Timings on a loaded machine ran 1.5 to 2 times the quiet values, and the clock check stays manual.

Exempting follow-up fixes from re-timing. The regression arrived in one.

</Fragment>
<Fragment slot="proof">

The fix pins the join order. SQLite does not reorder a `CROSS JOIN`:

```sql
fh AS (
  -- [...]
  SELECT b.session_id, b.match_id, b.grp_id, min(d.seq) AS first_hand_seq
  -- Cross joins fix the order hand -> decisions -> base -> k: left free, the planner
  -- starts at base and probes hand by grp_id alone (every hand row of the card, all games).
  FROM hand h
  CROSS JOIN decisions d ON h.session_id = d.session_id AND h.decision_id = d.decision_id
  CROSS JOIN base b ON b.session_id = d.session_id AND b.match_id = d.match_id
    AND b.game_number = d.game_number AND b.grp_id = h.grp_id
  CROSS JOIN k ON k.session_id = b.session_id AND k.match_id = b.match_id
    AND k.game_number = b.game_number AND k.anchor
  WHERE d.rolled_back = 0 AND d.seq >= k.keep_seq
  GROUP BY b.session_id, b.match_id, b.grp_id)
```

The work counter uses SQLite's progress handler, so the figure is exact from run to run and independent of machine load:

```rust
pub fn count_vm_work<T>(&self, f: impl FnOnce() -> T) -> (T, u64) {
    let ticks = Arc::new(AtomicU64::new(0));
    let seen = Arc::clone(&ticks);
    self.conn.progress_handler(
        1,
        Some(move || {
            seen.fetch_add(1, Ordering::Relaxed);
            false
        }),
    );
    let out = f();
    self.conn.progress_handler(1, None::<fn() -> bool>);
    (out, ticks.load(Ordering::Relaxed))
}
```

By the end of that sprint, with two further optimizations, the card tools went from about 300 ms to about 70 ms on the same 96-match store.

The budget is a net, not a guarantee. It later passed a slowdown of 1.5 to 2.3 times wall clock at only 1.05 to 1.11 times baseline, because its seed's card table held only the deck. The seed was enlarged.

</Fragment>
</Decision>

<Decision n={4} title="Hidden information has no field">
<Fragment slot="chose">

The overlay renders one snapshot type, and the set of keys it serializes is an allow-list checked by a test. The opponent's hand and library appear only as counts, and face-down cards only as a count. A new field fails that test until the list is changed in a reviewed commit.

</Fragment>
<Fragment slot="why">

The overlay should show only what a player could see at the table. Presenting inferred information about the opponent as fact is an anti-goal of the project.

</Fragment>
<Fragment slot="rejected">

Using the opponent's available actions. The log does contain them; the parser never reads them and no table stores them.

Reading the game client's memory.

</Fragment>
<Fragment slot="proof">

A test removes every action list from a recorded 25-match session and requires every derived table to come out identical. A control alters one of my own actions and requires the output to change.

The opponent-facing fields of the snapshot:

```rust
/// Hand zone length per side; `None` when the zone is absent or the seat unresolved.
pub hand_size: BySide<Option<u32>>,
/// Library zone `objectInstanceIds` length per side (never its contents).
pub library_count: BySide<Option<u32>>,
// [...]
/// The opponent's untapped battlefield lands; `None` when the battlefield zone is
/// absent or the seat unresolved.
pub opp_untapped_lands: Option<u32>,
/// Distinct grpIds, ordered by first sighting.
pub opp_revealed: Vec<Revealed>,
/// The opponent's face-down objects in public zones.
pub opp_face_down: u32,
```

One qualifier: the list of opponent cards already revealed does carry card ids. It is kept clean by a tested runtime filter, not by the shape of the type, and the filter admits a card first seen with no zone.

</Fragment>
</Decision>

<Decision n={5} title="The overlay is a separate read-only process">
<Fragment slot="chose">

The overlay is its own process, drawn with egui on the OpenGL backend. It opens the database read-only, never touches the log or the capture lock, and learns of new rows by polling SQLite's `PRAGMA data_version` every 250 ms with short reads. The rules for what to show live in the core library; the GUI only draws.

</Fragment>
<Fragment slot="why">

Capture must not depend on a window. With two processes and a read-only handle, a GUI crash cannot stop capture, and short autocommit reads never pin the write-ahead log.

</Fragment>
<Fragment slot="rejected">

The wgpu backend. In a spike it lost window transparency after one toggle and used 154 MB, against 72.5 MB for OpenGL.

</Fragment>
<Fragment slot="proof">

A source-scan test fails if the GUI or the live projection opens a writer.

In live play, the overlay and capture together measured 121.0 MiB and 1.78% of one core, against a budget of 150 MiB and 2%. The build one sprint earlier missed that budget at 181.5 MiB and 2.44%, and its retrospective says so.

</Fragment>
</Decision>

## How it was built

I built this as architect and product owner, with Claude Code agents doing the implementation. An AI controller ran each sprint and dispatched the agents. I set the goals and anti-goals, accepted each sprint against machine-checkable criteria, and ran the attended production migrations.

Three rules carried most of the quality:

- From the first sprint on, each task's test cases and mutations were designed and reviewed before implementation started.
- A second agent reviewed every task and re-ran hand-applied mutations. Implementers' own mutation counts did not predict what the reviewer found.
- A final review of the whole branch caught what the task reviews missed.

Three phases and seven sprints landed as 349 commits over ten working days between 2026-10-25 and 2026-11-12.

## What's next

The loop this was built for is not closed yet. Deck versions are identified and listed. Still to build: record a card swap as an experiment, let later games on the new version accrue to it, and report the difference with its uncertainty against two baselines, so ladder drift stays visible.
